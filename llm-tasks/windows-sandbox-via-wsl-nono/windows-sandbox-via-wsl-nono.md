# Run the Windows sandbox as nono under WSL2

Visual Relay ships three sandbox implementations for two behaviours. macOS and
Linux share one: the `nono` binary enforcing `vr-guard.json` through Seatbelt or
Landlock. Windows has its own, built on Microsoft Execution Containers
(`wxc-exec`), with a hand-authored policy generator that has to be kept in step
with `vr-guard.json` by hand. Replace the Windows one with nono running inside
WSL2, so every platform enforces the same profile through the same binary.

This is not a tidiness argument. The Windows sandbox cannot currently do the job
the macOS one does.

**Windows cannot deny credential reads.** `SandboxPathInspector.Windows.cs` says
so in its own comment: native enforcement of `filesystem.deniedPaths` is
feature-gated behind `Feature_BfsPolicyDeny` and is not shipped in the pinned MXC
release, so `WindowsDeniedPathsEnforced` is hardcoded `false` and every credential
denial VR surfaces in the UI carries a "may be readable" caveat. On macOS and
Linux the `deny_credentials`, `deny_keychains_*`, `deny_browser_data_*`,
`deny_shell_history` and `deny_shell_configs` groups are genuinely enforced by the
kernel. On Windows today an agent stage can read `~/.ssh`, `~/.aws`, browser
cookie stores and shell history. Writes are confined; reads of your secrets are
not. That gap is the reason to do this work, and no amount of policy-generator
polish closes it, because the enforcement is missing from the runtime.

**The Windows runtime is a release candidate.** `MxcInstaller.PinnedRelease` is
`v0.7.0-rc1` and `MxcPolicyGenerator.PinnedMxcVersion` is `0.7.0-alpha`. The
policy generator also carries a workaround for a fallback path that aborts the
whole run: when the BaseContainer backend is unavailable, MXC mutates DACLs and
stamps an ACE on every path in the policy, failing with "os error 3" on any path
that does not exist, which is why `MxcProvisioner` passes an existence-filtered
denial set. VR is carrying that complexity for a sandbox that does not enforce
denials anyway.

**WSL2 is Linux.** It runs the same kernel LSM nono already targets. The same
`nono` binary, the same `packaging/nono/vr-guard.json`, the same 27 resolved
groups, the same `nono profile show` output that `SandboxPathInspector` already
parses. The Windows arm stops being a second implementation and becomes a
launcher prefix.

## The trade this makes, stated plainly

Commands run in Linux. A target repo whose build or test command needs the
Windows toolchain (MSBuild against .NET Framework, Visual Studio build tools,
Unity on Windows, anything calling `.exe`) cannot be driven by Visual Relay after
this change. That is a real loss and it is the right trade: the alternative is
shipping a sandbox that confines writes while leaving credential reads open, on a
pinned release candidate, and maintaining a second policy language forever.

Make the loss loud rather than silent. The gate must name it, and the docs must
say Visual Relay on Windows drives repos whose toolchain runs in WSL.

## Current state (researched)

- **Mode selection** lives in `WindowsSandbox.Select`. After the swival sweep
  there are two modes left, `Mxc` and `Blocked`; execution is never silently
  unsandboxed.
- **The launch wrapper** is `WindowsSandbox.BuildMxcLaunch`, producing
  `wxc-exec.exe <policy.json> -- <program> <args…>`. The `--` is required or
  wxc-exec parses the program as its own flags.
- **The policy** is generated by `MxcPolicyGenerator.Generate` and written to
  `<config>/visual-relay/mxc-policy.json` by `MxcProvisioner.EnsurePolicy`,
  memoized per workspace. It is a hand-maintained parallel to `vr-guard.json`:
  workspace root plus per-ecosystem cache dirs under `filesystem.readwritePaths`,
  broad reads by default, `network.defaultPolicy = "allow"`, and an
  existence-filtered `filesystem.deniedPaths`.
- **The runtime** is self-provisioned by `MxcInstaller` from the signed
  `microsoft/mxc` release zip into `%LOCALAPPDATA%\visual-relay\mxc\`, exposed as
  the `provision-mxc` CLI verb (`ProvisionMxcCommand`).
- **The inspector** has a Windows partial, `SandboxPathInspector.Windows.cs`,
  building its result from the generator's inputs rather than from the sandbox
  binary, with the "may be readable" caveat described above.
- **Tests**: `WindowsSandboxTests`, `MxcInstallerTests`, `MxcRealSandboxTests`,
  `WindowsCredentialDenyTests`.
- **The bootstrap** is `visual-relay.ps1`, which provisions the toolchain natively
  because Nix has no Windows story, then execs the C# CLI. `visual-relay.cmd`
  wraps it.
- **The Unix prefix** VR already builds is
  `nono run --profile <abs vr-guard.json> --allow-cwd [-a <path>]… [--rollback
  --no-rollback-prompt] -- <cmd>`, from `SandboxedStage.BuildNonoPrefix`. The
  profile is written by `NonoProfileEnsurer` to
  `$XDG_CONFIG_HOME/visual-relay/vr-guard.json` and overwritten on every run.
- **`vr-guard.json` no longer extends anything third-party.** It extends nono's
  built-in `default` and declares its own groups, `workdir.access: "readwrite"`,
  and security settings, so nothing has to be pulled from a registry before it
  resolves. A fresh WSL distro needs only the nono binary.

## What to build

### 1. Prove the premise before building on it

Do this first and record the numbers. If either probe fails, stop and report
rather than working around it.

- **Landlock in the stock WSL2 kernel.** Confirm the LSM is present and active
  (`/sys/kernel/security/lsm`, and nono's own diagnostics). Microsoft's WSL2
  kernel config decides this, and it may need `lsm=` on the kernel command line
  via `.wslconfig`. If it needs configuration, that configuration becomes part of
  the gate's install instructions, not an assumption.
- **Landlock across the DrvFs boundary.** Put a scratch workspace under
  `/mnt/c/...` and run a real nono confinement probe against it: a write inside
  the workspace must succeed, a write to a denied path must fail. Then repeat
  with the workspace on the distro's own ext4. If DrvFs does not enforce, that
  settles item 3 below.

### 2. A WSL gate that mirrors the nono gate

Add the Windows analogue of `NonoGate`. It must check, and name in its failure
message, each of: WSL is installed, a WSL2 (not WSL1) distro is available, the
`nono` binary resolves inside that distro, and Landlock is active there. Follow
`NonoGate.Decide`'s shape: a pure function returning `(exit code, message)` so it
is unit-testable, with the process probing split out.

The message must state the toolchain consequence, not just the missing
dependency. Something a user can act on: which distro to install, how to install
nono in it, and that their project's build and test commands will run inside that
distro.

Let the distro be selectable (`VR_WSL_DISTRO`), defaulting to the WSL default
distro. Never fall back to running unsandboxed.

### 3. Decide where the workspace lives, and enforce it

Recommended: require the workspace on the distro's own filesystem and refuse
`/mnt/*` paths, on both correctness and speed grounds. DrvFs is roughly an order
of magnitude slower for the many-small-files access pattern a build produces, and
its permission model is not the one Landlock was designed against.

If the probe in item 1 shows DrvFs enforces correctly, downgrade the refusal to a
warning that names the performance cost. Either way the decision must be explicit
in the code and covered by a test, not left to chance.

The Windows folder picker must accept a `\\wsl$\<distro>\...` UNC path and
translate it to the Linux path VR hands to WSL. Put that translation in one place
with tests for both directions, including spaces and non-ASCII.

### 4. One launcher, not a string-concatenation hazard

Add the WSL equivalent of `BuildNonoPrefix`: given the program and its argument
list, produce the `wsl.exe` invocation that runs it under nono inside the distro.

The single biggest risk in this task is quoting. A command crosses two shells
(the Windows argument encoder and the Linux shell) and will be mangled by naive
concatenation. Do not build one string. Either use `wsl.exe --exec` with an argv
array so no Linux shell re-parses the arguments, or write the command to a
temporary script inside the distro and run that. Test with arguments containing
spaces, double quotes, single quotes, backslashes, `$`, backticks, newlines, and
non-ASCII, and assert on what the child process actually received rather than on
the string VR built.

Reuse `vr-guard.json` verbatim. The profile is written by `NonoProfileEnsurer` on
the Windows side, so it must be placed where the distro can read it: write it
inside the distro rather than pointing nono at a `/mnt/c` path, and keep the
overwrite-always behaviour so it can never go stale.

### 5. Make the watchdog work across the boundary

This will not work by accident. `ProcessCapture.GracefulStop` and
`ProcessTreeCpuSampler` assume the child process tree is visible to the host.
Killing `wsl.exe` on the Windows side does not reliably kill the Linux process
tree, and Windows cannot see Linux process CPU time, so the stall detector loses
its `cpu` signal and the timeout ceiling loses its ability to actually stop work.

Both need a WSL-aware path. Sample CPU from inside the distro, and stop the tree
from inside the distro by pid or process group. Prove it with a test that starts
a deliberately hung command and asserts the Linux process is gone afterwards, not
merely that `wsl.exe` exited.

Check the same boundary for stdout and stderr: confirm UTF-8 survives, and that
exit codes propagate rather than collapsing to a generic wsl.exe failure.

### 6. Route git through the same view

VR runs git itself through `GitInvoker`, against the workspace. With the workspace
inside the distro, git-for-Windows over `\\wsl$\` UNC paths is slow and has
line-ending and permission semantics that differ from the git the agent sees
inside the sandbox. Two different git views of one repo will produce confusing
diffs and commit-gate failures.

Run VR's git through WSL as well, so there is exactly one filesystem view. This
is the largest single piece of work in the task and it deserves its own commit
and its own test pass. If measurement shows the UNC path is acceptable, say so
with numbers rather than assuming.

### 7. Delete the MXC path

Once the WSL path passes, remove `WindowsSandbox`'s MXC arm, `MxcPolicyGenerator`,
`MxcProvisioner`, `MxcInstaller`, `ProvisionMxcCommand`, the `provision-mxc` verb,
`SandboxPathInspector.Windows.cs`, and their tests. Do not leave both paths behind
a flag. Two sandboxes is the problem this task exists to solve.

The Windows arm of `SandboxPathInspector` then goes away entirely: on Windows the
inspector shells the same `nono profile show` through WSL that Unix does, so the
"may be readable" caveat disappears because the denials are actually enforced.
That is the outcome to demonstrate in the report.

### 8. Docs and packaging

Update `README.md`, `TROUBLESHOOTING.md`, `docs/OPERATIONS.md` and `AGENTS.md` to
describe the Windows requirement and the toolchain consequence. `visual-relay.ps1`
provisions the native toolchain today; decide what it still needs to provision
once commands run in the distro, and shrink it accordingly. Say in the docs that a
Windows-toolchain repo is not supported, so nobody discovers it as a bug.

## Done when

- On a Windows box with WSL2, a real task runs end to end through the desktop app
  and commits, driven through the control API the way the macOS validation is
  done.
- `SandboxPathInspector` on Windows returns the same 27 groups and the same
  resolved policy as macOS, with no "may be readable" caveat anywhere in the UI.
- A confinement probe run on Windows produces the same verdicts as macOS for:
  workspace write, workspace delete, git, a toolchain cache write, `~/Documents`
  write denied, `~/.ssh` read denied, network reachable, and `/usr/bin` readable.
  The `~/.ssh` row is the one that fails today.
- The watchdog kills a deliberately hung command and the Linux process is gone.
- No MXC code, tests, verb, or docs remain.
- The full suite is green and `./visual-relay check` exits 0 with 0 inspect-code
  findings.

## Rejected alternatives

**Run the whole app inside WSL under WSLg.** Much cheaper, since the Linux build
already exists and needs no new code at all. Rejected because the product is a
Windows desktop app: the launcher, packaging, restart handling and folder picker
are all native, and moving the GUI to WSLg trades a working Windows app for a
Linux app that happens to render on Windows. Revisit only if items 4 through 6
prove more expensive than expected, and note that this fallback stays available
the entire time.

**Wait for `Feature_BfsPolicyDeny` to ship.** That would close the credential-read
gap without any of this work. Rejected because it leaves the schedule in
Microsoft's hands, leaves the parallel policy language in place, and leaves VR
pinned to a release candidate in the meantime. If it ships before this task is
picked up, the maintenance argument still stands on its own.

**Keep MXC for Windows-toolchain repos and add WSL alongside.** Rejected: it is
the current situation plus a third implementation, and it makes the sandbox
guarantee depend on which repo you opened.
