Stop() blocks the caller via `Task.Run(...).GetAwaiter().GetResult()`, which does not return until the inner task completes; if StopAsync truly ignored the token and never completed, the caller WOULD hang. The comment is internally inconsistent (an abandoned/incomplete pool thread is incompatible with a non-hanging caller). The actual guarantee is that `IHost.StopAsync(CancellationToken)` honors the token and forces shutdown at 5 s — not thread-pool abandonment. This misrepresents the task's required 'bounded teardown / never hang' contract and is a latent footgun (a maintainer could remove the CancellationToken believing the offload is the safety net). Fix: reword the comment to state that the 5 s CancellationToken passed to app.StopAsync is what bounds teardown, and that the thread-pool offload exists only to avoid sync-back to the Avalonia dispatcher, not to bound the wait.
